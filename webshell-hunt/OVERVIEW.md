# webshell-hunt 总览

一个用来练习「服务器已经被入侵，把后门全找出来」的靶场。

不是打靶，是应急响应（IR）里的静态排查训练。CTF 是从已知入口打到 flag，这里反过来：服务器已经在攻击者手里，你不知道有几个后门、不知道在哪、也不知道有没有漏，只能靠命令行自己翻。

---

## 一、这件事在真实世界里长什么样

护网或者应急响应接到的电话通常是：「我们网站被挂了马，你帮看看。」

对方不会告诉你：

- 有几个后门
- 在哪个目录
- 什么时候进来的
- 从哪个漏洞进来的

大部分情况你拿到的是一个 SSH 账号，一台跑了三年、几万个文件的机器。

**和 CTF 的关键区别**：

- CTF 有明确的入口和明确的 flag，路径是收敛的
- IR 没有边界，你永远无法证明「全找完了」，只能靠多个维度交叉，尽量逼近「全找完了」

这也是为什么真实报告里最常出现的词是「已发现的」而不是「全部」。

---

## 二、webshell 是什么

一句话：**一段放在服务器上、通过 HTTP 请求触发代码执行的脚本。**

它能起作用必须同时满足三个条件，这三个条件同时也是排查的三个切入点：

1. **能被访问到** —— 文件落在 web 根目录下，路径能拼出来
2. **能被解析** —— `.php` 后缀，或者被 `.htaccess` 强行指定给 PHP 解释器
3. **参数可控** —— 攻击者发来的内容会被当成代码或命令

后门的各种变种，本质都是在动这三个条件：

- 图片马：绕开条件 2 的检查（上传只校验图片），靠 `.htaccess` 补上
- 混淆马：让条件 3 的入口不容易被看出来
- session 投毒：文件放不到可访问位置，等一个 LFI 漏洞来包含它
- 内存马：三个条件都不出现在磁盘上（本靶场未覆盖，但要知道存在）

---

## 三、为什么难查

三个原因，从易到难：

**1. 量大**

几万个正常文件里找几个几百字节的文件。逐个人肉看是不现实的，必须有筛选策略。

**2. 会伪装**

- 改时间戳，让文件看起来和站点同龄
- 改权限，或者用点开头让 `ls` 看不见
- 拆函数名（`'sys' . 'tem'`），让关键词扫描失效
- base64 编码，让人看不出逻辑
- 混进正常代码末尾，靠注释撒谎

**3. 可能不止一个**

删掉一个不算完。而且**删文件不等于修好**——只要漏洞还在，攻击者能重新放回来。

靶场里那个 session 投毒文件就在提示这件事：站点还有文件包含漏洞没被找到，投毒文件只是证据。

## 四、靶场怎么设计的

**规模**：25 个文件（23 个在 web 根目录，2 个在外围），9 个后门 + 1 个诱饵。

**分四层，对应四种能力**：

- **L1**：会 `grep` 关键词就能找到 → 检验基础工具使用
- **L2**：能读懂上下文 → 检验「这段代码的业务理由是不是编的」这个判断力
- **L3**：会看元数据 → 检验是否知道要查权限、属主、隐藏文件，而不是只看内容
- **L4**：会解码、会想到 www 之外 → 检验排查视野

**真实感来源**（这些细节是刻意造的）：

- 时间线分两段：基线 2025-11，入侵集中在 `2026-10-20` 凌晨 3 点半到 3 点 44 的 6 分钟内，像人操作的速度，不是运维发版
- 后门的属主是 `www-data`，所在目录属主是 `root` → Web 进程写进 root 目录，说明有任意文件写入
- 日志里混着正常访客、Googlebot、扫描器，攻击者的 20 条请求只占一部分（这是真实噪音）
- 攻击链路完整：扫描插件 → 爆破 wp-login → 落地 shell → 传图片马 → 改 `.htaccess` → 执行命令

**诱饵的作用**：

`wp-admin/admin-ajax.php` 里有 `call_user_func( $handlers[ $action ] )`，看着像动态调用后门，实际 `$action` 被白名单限制住了。

误报和不报一样有害——真实报告里塞满噪音，看报告的人会直接失去信任。

## 五、九个后门和线索的对应关系

这张对应表是整个靶场的设计核心。它说明一件事：**任何一个单一维度都会漏，必须交叉。**

### 时间线直接能捞到的（6 个）

跑一次 `find -newermt` 就能看到，因为它们的时间戳都停在入侵那 6 分钟里：

- `wp-includes/simple.php`
- `upgrade.php`
- `wp-content/uploads/2026/03/.htaccess`
- `wp-content/uploads/2026/03/logo.jpg`
- `wp-content/uploads/2026/03/index.php.bak`
- `wp-content/mu-plugins/loader.php`

这 6 个是「及格线」。只做到这一步，说明只用了一个维度。

### 时间线完全看不到，必须靠内容扫描（1 个）

- `wp-content/themes/twentytwenty/functions.php`

mtime 被 `touch` 回了主题安装当天，和 `style.css` 一模一样（`2025-11-12 09:31`）。`find -newermt` 永远抓不到它，只能靠 `grep` 命中那行 `eval( $cache )`，再读上下文判断。

**这是整个靶场最重要的一课**：伪造时间戳是常规操作，不是高级技巧。

### 时间线看不到，靠元数据兜底（1 个）

- `wp-content/plugins/cache/.wp-check.php`

三重伪装：

- 文件名以点开头 → `ls` 看不见
- mtime 改到 `2024-06-12` → 比站点上线还早一年
- 权限 `600` → 全站唯一一个不是 `644` 的 php

发现它的方式是元数据：`find -name '.*'`、`! -perm 644`、`-user www-data`。

顺带一提，它的时间比目录创建时间还早，这在真实取证里是**逻辑矛盾**级铁证——一个文件不可能在它所在目录被创建之前就存在。

### 完全在 web 目录之外（1 个）

- `/var/tmp/sess_a3f9c2e1b7d4`

所有以 `/var/www/html` 为根的命令都捞不到它。内容是 PHP 的 session 序列化格式，里面塞了 `<?php @system(...) ?>`。

正常 session 在 `/var/lib/php/sessions`，这个却在 `/var/tmp`，而且时间正好落在入侵窗口内。

**它的意义不在本身**——session 投毒不能自己执行，必须有 LFI 配合。发现它等于被告知：还有别的漏洞没找到。

## 六、练完能得到什么

**一套可以搬走的命令**

不是靶场专用的 hack，是真实服务器上能直接用的 `find` / `grep` / `stat` 组合。具体在 `answer/ANSWERS.md` 第三节。

**一个改变直觉的习惯**

先看时间分布，再找文件。不是上来就 `grep eval`。

时间分布能在一分钟内告诉你「哪一天异常」，把范围从几万个文件缩到几十个。这是性价比最高的一步。

**对痕迹的理解**

以后遇到没见过的后门变种，你会知道该往哪个维度找：

- 改时间戳的 → 查逻辑矛盾、比对官方版本
- 拆函数名的 → 扫变量函数调用
- 编码的 → 扫编码函数组合，然后手动解码
- 藏文件的 → 扫元数据
- 不在 web 目录的 → 扫临时目录、session、日志

**一个边界感**

删文件 ≠ 修好。修漏洞才有意义。真实应急里「二次失陷」非常常见。

## 七、怎么开始

```bash
docker exec -it webshell-hunt bash
cd /var/www/html
find /var/www/html -type f -printf '%TY-%Tm-%Td\n' | sort | uniq -c
```

第三条给你一张按天统计的时间分布表。看哪一天突然扎堆，那就是入侵窗口。

完整操作步骤见对话里的七步走，或者直接看 `answer/ANSWERS.md` 第三节。
